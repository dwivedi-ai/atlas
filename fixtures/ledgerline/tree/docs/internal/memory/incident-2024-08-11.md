# Incident, 2024-08-11 — stale index after insert

**Impact:** one consumer's nightly reconciliation produced a trial balance that
omitted every transaction added after the ledger was first queried. Two nights,
caught on the third.

**Duration:** introduced in 0.5.0 (2024-07-19), fixed in 0.5.1 (2024-08-12).

## What happened

`Ledger.add` appended and re-sorted, but did not clear `_by_account`. Anything
that had already called `index_by_account()` kept the pre-insert index forever,
because the cache check was `if self._by_account is None`.

The consumer's pattern was:

```python
ledger = Ledger.load(path)
report_a = run("trial-balance", ledger, options)   # builds the index
ledger.extend(late_arrivals)                       # does not clear it
report_b = run("trial-balance", ledger, options)   # uses the stale index
```

Nothing raised. The second report was internally consistent and simply smaller.

## Why it took three nights

The residual check would have caught it — a trial balance missing one side of a
transaction has a non-zero residual — but `meta["residual"]` did not exist until
0.7.0. It was added *because of this*, and the entry in `docs/changelog.md` for
0.7.0 undersells the reason.

The suite did not catch it because every test built a ledger, then queried it,
and never did both twice. `test_ledger.py::test_index_by_account_is_rebuilt_after_a_mutation`
is the test that would have.

## Fix

`Ledger._invalidate()` clears both caches; `add` calls it. `extend` calls `add`,
so it is covered transitively. Deliberately not a partial invalidation: see
`../architecture.md`.

## Follow-ups

- [x] `_invalidate` and its test (0.5.1)
- [x] `meta["residual"]` on the trial balance (0.7.0)
- [x] Runbook entry for "the report is missing recent transactions"
- [ ] A test that mutates a ledger between two report runs and compares. The
      unit test covers the index; nothing covers the pattern end to end.

## What we would do differently

The cache was added for a performance problem that had not been measured. The
index rebuild is 0.11 s on the largest document anyone has (see
`../performance-notes.md`), so the cache was buying nothing and cost two nights
of someone else's numbers.
